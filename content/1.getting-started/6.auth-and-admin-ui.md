[Outlabs Auth](https://auth.outlabs.io/) supplies identity and permission
checks. [Auth UI](https://auth.outlabs.io/integrations/outlabsauth-ui/) manages
those Auth records. TaskQ runs and schedules jobs. The
[combined architecture and setup path](https://auth.outlabs.io/integrations/taskq/)
explains where each component belongs.

TaskQ works without Auth. Choose this integration when your FastAPI host
already uses Auth and you want its identities to authorize TaskQ HTTP calls.
Auth UI is an optional identity console; queue and job operations use the
[TaskQ CLI](/getting-started/cli).

## Install and prepare the host

```bash [Terminal]
pip install "outlabs-taskq[outlabs]==0.1.0a42" "outlabs-auth==0.1.0a37"
```

Complete the [Auth quickstart](https://auth.outlabs.io/getting-started/getting-started/)
and [TaskQ quickstart](/getting-started/quickstart). Run each library's migrations
through its own release step. Prepare the queue, target binding and
[SQL capability roles](/getting-started/install#capability-roles) before
connecting runtime processes.

## Mount the Auth-backed facade

Add this function to the host that owns your existing Auth instance and TaskQ
resources. It is an integration fragment, not a standalone application:

```python [taskq_integration.py]
from fastapi import FastAPI
from taskq.http import TaskqFacadeTransports, create_taskq_app
from taskq.http.outlabs import OutlabsQueueAuthorizer


def mount_taskq(host: FastAPI, auth, resources: TaskqFacadeTransports):
    async def auth_session():
        async with auth.get_session() as session:
            yield session

    authorizer = OutlabsQueueAuthorizer(
        auth=auth,
        session_dependency=auth_session,
    )
    host.mount("/taskq", create_taskq_app(resources, authorizer=authorizer))
```

Before calling it, construct Auth and call `auth.prime_fastapi_routing()` so
its dependencies exist. Initialize Auth before serving requests and shut it
down in the host lifespan. `resources` is the host's `TaskqFacadeTransports`
with producer, runner, observer, authorization lookup and claim-wait hub;
see [HTTP facade](/api/http-facade) for that wiring. The host owns startup and
cleanup of those resources. This function starts no worker or scheduler.

The facade calls Auth's supported authenticate/authorize API; it does not
interpret raw scope dictionaries. It uses the Auth session provider for policy
checks and TaskQ's SQL transports for jobs. Operator HTTP routes require both
`operator_transport` and `operator_authorizer` when constructing the facade;
the minimal fragment above does not mount them.

## Provision permissions and assign credentials

Use the [authorization guide](/api/authorization#provisioning) to review and
apply TaskQ's catalog. A direct-SQL IAM provisioning context must also select
`auth_dsn_env` for the Auth database, even if both libraries share a server.
For example, keep a separate setup context with secret variable names:

```toml [config.toml]
version = 1

[contexts.iam_setup]
transport = "sql"
dsn_env = "TASKQ_MIGRATION_DSN"
auth_dsn_env = "AUTH_DATABASE_DSN"
expected_environment = "staging"
actor = "operator:iam-setup"
```

Supply both DSNs through the setup process's secret environment. If Auth uses
a custom schema, set `TASKQ_AUTH_SCHEMA` to that schema. Review before apply:

```bash [Terminal]
taskq --context iam_setup auth plan --queues mail --per-queue-roles -o json
taskq --context iam_setup --yes auth apply --queues mail --per-queue-roles \
  --plan-digest "$PLAN_DIGEST" -o json
```

Take `PLAN_DIGEST` from the reviewed plan, not from a different target. Default
standard roles cover global actions; `--per-queue-roles` adds queue-specific
worker roles as well. Inspect the resulting grants before assigning one.
Creating the catalog does not grant a user or machine access.

| Caller | Typical queue-scoped Auth permissions |
| --- | --- |
| Producer | `taskq_mail:enqueue`, plus `taskq_mail:read` when needed |
| Worker | `taskq_mail:run`, `taskq_mail:read` |
| Queue operator | `taskq_mail:control`, `taskq_mail:read` |
| Administrative setup | `taskq_mail:admin` only when required by the selected endpoint |

Global names such as `taskq:run` cover all queues and are broader than
`taskq_mail:run`. Literal wildcard scopes are not
supported for API keys. Inspect the [authorization contract](/api/authorization)
and the endpoint's required action before granting a credential.

Use Auth UI's Users, Roles and Permissions to administer human access, and
Service accounts where the host supports integration principals and keys.
See [Auth API keys](https://auth.outlabs.io/integrations/api-keys/) for personal
versus system-key policy and [Auth CLI](https://auth.outlabs.io/build/cli/) for
scripted administration. Auth's credential policy can further restrict a
source even when a role contains a permission. Prove the chosen machine
credential on the exact preset and host; broad human-admin credentials are
not a worker setup.

### Private metadata and queue-scoped workers

The packaged facade defaults to private target metadata. The stock Auth
adapter checks that metadata with global `taskq:read`; queue-only
`taskq_mail:read` does not satisfy the CLI/worker identity handshake. Granting
`taskq:read` also permits reads across queues. Decide that broader read access
explicitly, or qualify a host-owned metadata/authorizer policy before using a
strictly queue-scoped worker. The table above describes queue actions, not a
complete private-metadata credential.

## Connect an HTTP worker

A secret-free context for an Auth bearer/service token:

```toml [config.toml]
version = 1

[contexts.mail_worker]
transport = "http"
base_url = "https://api.example.com"
bearer_token_env = "MAIL_WORKER_TOKEN"
expected_environment = "staging"
expected_installation_id = "018f0000-0000-7000-8000-000000000000"
```

Replace the URL, environment and installation UUID with the reviewed target.
The base URL is the host origin for the packaged `/taskq/v1/...` mount. It is
independent of the Auth UI's `authApiPrefix`. Supply `MAIL_WORKER_TOKEN` through
the worker supervisor or secret manager; Auth and the host own issuance and
renewal. The CLI does not log in through Auth UI or refresh a human session.

For a permitted Auth API key, replace `bearer_token_env` with the paired
`header_name = "X-API-Key"` and `header_value_env = "MAIL_WORKER_API_KEY"`.
Use exactly one credential source. Key scopes and source policy must allow
both the worker's read and run actions. EnterpriseRBAC personal keys reject
`run`; use a qualified service token or permitted system/integration key
instead. SimpleRBAC and system-key action policies differ, so a role alone
does not prove a key is usable.

```bash [Terminal]
# First verify the target and that this credential exposes the required capabilities.
taskq --context mail_worker capabilities -o json
# myapp.tasks:registry must be importable in the worker's installed application.
taskq --context mail_worker worker run \
  --registry myapp.tasks:registry --queue mail --environment staging --no-listen
```

HTTP workers receive no TaskQ database credential. The facade holds the
restricted SQL credentials. An application handler that accesses its own
business database still needs that application's access.

## Scheduling and Auth maintenance

Run [one standalone scheduler](/operations/standalone-scheduler) with its own
attested database identity. Auth UI does not configure schedules or operate
queues. For periodic Auth cleanup, register an application task that invokes
`auth.run_maintenance_once()`; see
[Auth's maintenance pattern](https://auth.outlabs.io/getting-started/background-maintenance/#optional-taskq-pattern).
That handler needs Auth database and configured Redis access. Keep embedded
Auth maintenance disabled in API replicas and start the schedule paused.

## Check the complete path

1. Sign in through Auth UI and verify the host's users, permissions and profile.
2. Verify the worker credential can read/run `mail` and cannot run/control an
   unrelated queue. Check whether cross-queue reads match the metadata policy
   you explicitly selected.
3. Enqueue one keyed job and observe one terminal result with the TaskQ CLI.
4. If using schedules, prove one occurrence and keep one scheduler owner.
5. Exercise expiry/refusal of the configured credential and verify the host's
   renewal/recovery procedure. A working console login alone does not prove
   worker access.

Database queue admission ownership and Auth HTTP permissions are independent
checks. Follow [queue boundaries](/operations/queue-boundaries) and
[runtime-first upgrades](/operations/runtime-first-upgrades) for production.
