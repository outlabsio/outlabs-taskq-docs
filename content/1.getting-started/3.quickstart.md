Use a fresh, disposable local PostgreSQL 16+ database and Python 3.12+.
This tutorial uses its database administrator for a short local demo. A deployed
host needs separate least-privilege credentials and the
[queue ownership boundary](/operations/queue-boundaries).

```bash [Terminal]
python -m venv .venv
source .venv/bin/activate
pip install outlabs-taskq==0.1.0a42
```

Run all Python commands below from the same directory.

## 1. Migrate

Create `~/.config/taskq/config.toml` and export the credential:

```toml
version = 1

[contexts.development]
transport = "sql"
dsn_env = "TASKQ_DEVELOPMENT_DSN"
expected_environment = "development"
actor = "operator:developer"
```

```bash
export TASKQ_DEVELOPMENT_DSN='postgresql://postgres:postgres@localhost:5432/myapp'
taskq --context development db plan -o json
taskq --context development --yes db migrate --plan-digest "$PLAN_DIGEST"
taskq --context development db plan -o json
# Read TASKQ_INSTALLATION_ID from data.target.installation_id in this plan.
taskq --context development --yes \
  --expected-installation-id "$TASKQ_INSTALLATION_ID" \
  target bind development --expected-binding-version 0
taskq --context development db plan -o json
taskq --context development --yes db migrate --plan-digest "$PLAN_DIGEST"
taskq --context development db verify
```

Extract each fresh `PLAN_DIGEST` and the installation UUID from the preceding
JSON envelope after reviewing it. The first migration deliberately exits `1`
with `TQ422` / `target_unbound` after installing migration 0019. Use `db plan`
to read its installation identity, bind it, then review a fresh digest before
resuming migrations. In published a42, `target show` rejects an unbound target
when the context already declares `development`; use the plan for this step.

## 2. Create the demo queue

Save the queue profile and create it explicitly; enqueue and worker startup
do not create queues for you.

```json [queue.json]
{
  "default_lease_seconds": 120,
  "default_max_attempts": 3
}
```

```bash [Terminal]
taskq --context development queue ensure demo --input queue.json
taskq --context development queue resume demo
```

The context's actor identifies these operator writes. Keep this example
context pointed only at the disposable development database.

## 3. Define a task

```python [tasks.py]
from pydantic import BaseModel

from taskq import Task, TaskRegistry


class Input(BaseModel):
    value: int


class Output(BaseModel):
    doubled: int


async def double(payload: Input) -> Output:
    return Output(doubled=payload.value * 2)


DOUBLE = Task(
    name="demo.double",
    queue="demo",
    input_model=Input,
    output_model=Output,
    handler=double,
)

registry = TaskRegistry((DOUBLE,))
```

Handlers take `(payload)` or `(JobContext, payload)`. Returning the output model is treated as success; you can also return `Complete`, `Snooze`, `Cancel`, `Retry`, or `NonRetryable` explicitly.

## 4. Enqueue

Save this alongside `tasks.py`:

```python [enqueue.py]
import asyncio
import os

from taskq import TaskQ
from tasks import DOUBLE, registry


async def main():
    tq = TaskQ.from_dsn(os.environ["TASKQ_DEVELOPMENT_DSN"], registry=registry)
    try:
        result = await tq.enqueue(DOUBLE, {"value": 3}, idempotency_key="demo:3")
        print(result.model_dump_json())
    finally:
        await tq.aclose()


if __name__ == "__main__":
    asyncio.run(main())
```

```bash [Terminal]
python enqueue.py
```

The first active insert reports `created`; replay while it is active reports
`existed`. `TaskQ` is a producer facade: configuring a registry does not start
a claim loop. The producer uses the same named environment variable as the
CLI context, so it reaches the database you just migrated.

## 5. Run a worker

```bash
PYTHONPATH=. taskq --context development worker run \
  --registry tasks:registry \
  --queue demo \
  --environment development
```

`PYTHONPATH=.` makes the local `tasks.py` importable by the installed CLI.
Point `--registry` at a `module:attr` that exports a `TaskRegistry`. For local smoke tests without NOTIFY, add `--no-listen --poll-interval 0.5`.

## 6. Verify the result

In a second terminal, activate the same virtualenv and run:

```bash [Terminal]
taskq --context development job list --queue demo --view finished -o json
taskq --context development job show JOB_ID --include-result -o json
```

Replace `JOB_ID` with the ID from enqueue or the finished-job list. A successful
job contains `{"doubled": 6}`. Stop the worker with Ctrl-C when the demo is done.
If no job finishes, check the worker's database target, that `demo` is resumed,
and that `tasks:registry` imports from your current directory.
