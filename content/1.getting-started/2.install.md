Published via [GitHub Releases](https://github.com/outlabsio/outlabs-taskq/releases)
(not PyPI). Pin the exact `0.1.0a23` wheel:

```bash
pip install https://github.com/outlabsio/outlabs-taskq/releases/download/v0.1.0a23/outlabs_taskq-0.1.0a23-py3-none-any.whl

# with extras:
pip install "outlabs-taskq[http] @ https://github.com/outlabsio/outlabs-taskq/releases/download/v0.1.0a23/outlabs_taskq-0.1.0a23-py3-none-any.whl"
pip install "outlabs-taskq[outlabs] @ https://github.com/outlabsio/outlabs-taskq/releases/download/v0.1.0a23/outlabs_taskq-0.1.0a23-py3-none-any.whl"
```

Requires **Python 3.12+** and **PostgreSQL 16+** (18 is the preferred deploy target).

## Dependency tiers

| Install | What you get | Hard deps |
|---|---|---|
| `outlabs-taskq` | Migrator, models, asyncio SQL client, worker loop, CLI | pydantic, sqlalchemy[asyncio], asyncpg, croniter |
| `[http]` | Facade app + HTTP clients + claim-wait hub | fastapi, httpx |
| `[outlabs]` | OutLabs queue authorizer + IAM provisioning | `[http]` + `outlabs-auth>=0.1.0a27,<0.2.0` |

::note
`import taskq` must succeed without FastAPI and without `outlabs-auth`.
::

## Install the schema

Use the CLI (preferred) or call the migrator from your host migration tool:

```bash [Terminal]
export TASKQ_DSN='postgresql://taskq_migration:...@localhost:5432/myapp'

taskq migrate
taskq target show --json
taskq target bind development --actor local-setup \
  --expected-installation-id '<installation-uuid>' \
  --expected-binding-version 0
taskq migrate
taskq verify
```

On a fresh `a23` install, the first `migrate` intentionally commits migration
`0019` and stops before `0020` while the target is unbound. Inspect the safe
fingerprint, bind the intended environment using the reported installation
UUID, then resume migration. Never let the package infer an environment from a
database hostname.

```python
from taskq.sql import migrate_sync, verify_sync

def upgrade():
    # Alembic / host revision — run as a Postgres admin that can create roles
    migrate_sync(op.get_bind())
    report = verify_sync(op.get_bind())
    assert report.ok
```

There is no `install()` helper. `migrate` applies packaged SQL (`0001`–`0020`)
under an advisory lock; `verify` is the read-only drift oracle (catalog,
grants, checksums) for SQL contract **0.3.0**. Run both with a dedicated owner
deployment credential, not a runtime capability role.

::caution
Remove the owner credential after migrate/bind/verify. APIs, workers, and the
scheduler need only their restricted TaskQ capability roles.
::

## Capability roles

The installer creates six roles (ADR-010):

| Role | Purpose |
|---|---|
| `taskq_owner` | Owns schema objects |
| `taskq_producer` | Enqueue |
| `taskq_runner` | Claim / heartbeat / settle |
| `taskq_observer` | Stats / read views |
| `taskq_operator` | Redrive / cancel / control |
| `taskq_housekeeper` | Tick / reaper |

Host apps call `migrate` / `verify` — do not fork the SQL in-tree.
