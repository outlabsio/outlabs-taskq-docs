The `outlabs-taskq` package installs `taskq` and `taskq-bench`.

| Command | Purpose |
|---|---|
| `taskq migrate` | Apply packaged migrations under an advisory lock |
| `taskq verify` | Read-only manifest and catalog drift check |
| `taskq target show` | Read the safe database target fingerprint |
| `taskq target bind` | Bind an environment or explicitly rotate a clone identity |
| `taskq worker` | Run a DB-direct or HTTP worker |
| `taskq scheduler` | Run the framework-neutral recurring-work clock |
| `taskq scheduler doctor` | Read-only target and scheduler-health preflight |
| `taskq schedule plan` | Render a non-mutating source-manifest plan |
| `taskq schedule apply` | CAS-apply desired schedules without implicit pruning |
| `taskq schedule retire` | Explicitly retire one source-owned manifest key |
| `taskq auth sync-permissions` | Report/apply OutLabs IAM rows (`[outlabs]` required) |
| `taskq-bench run` | Run report-only benchmark scenarios |

## Credential safety

Prefer environment variables so password-bearing DSNs and tokens do not enter
shell history or process arguments:

```bash [Terminal]
export TASKQ_DSN='postgresql://restricted_role:...@db-host/app'
export TASKQ_EXPECTED_ENV='staging'
```

Use a privileged owner credential only for migrate, bind/rotate, and verify.
Workers, APIs, manifest operators, and schedulers should receive distinct
restricted runtime credentials.

## Worker

Configure exactly one transport: `TASKQ_DSN` or `TASKQ_HTTP_BASE_URL`.

```bash [Terminal]
export TASKQ_DSN='postgresql://taskq_runner:...@db-host/app'
export TASKQ_EXPECTED_ENV='staging'

taskq worker \
  --registry myapp.tasks:registry \
  --queue mail \
  --queue courts \
  --environment staging \
  --concurrency 4 \
  --batch 2
```

HTTP workers do not need database credentials:

```bash [Terminal]
export TASKQ_HTTP_BASE_URL='https://api.example.com/taskq'
export TASKQ_HTTP_BEARER_TOKEN='...'

taskq worker \
  --registry myapp.tasks:registry \
  --queue mail \
  --environment staging \
  --no-listen
```

Most knobs load from `TASKQ_*` variables via `WorkerSettings`. HTTP workers
cannot use PostgreSQL `LISTEN`.

## Scheduler and manifests

```bash [Terminal]
export TASKQ_DSN='postgresql://taskq_scheduler:...@db-host/app'
export TASKQ_EXPECTED_ENV='staging'

taskq scheduler doctor --json
taskq schedule plan schedules.yaml --json
taskq schedule apply schedules.yaml --actor release-agent
taskq scheduler

# Bounded mode for a platform or OS timer:
taskq scheduler --once --json
```

Production additionally requires a static installation UUID pin and explicit
opt-in:

```bash [Terminal]
export TASKQ_EXPECTED_ENV='production'
export TASKQ_EXPECTED_INSTALLATION_ID='<production-installation-uuid>'
export TASKQ_ALLOW_PRODUCTION='true'
```

Scheduler and worker settings read that production opt-in from the environment.
The `target bind`, `schedule apply`, `schedule retire`, and `scheduler doctor`
operator commands additionally require an explicit `--allow-production` flag.

Read [Standalone Scheduler](/operations/standalone-scheduler) before activating
a recurring manifest.

## Auth provisioning

```bash [Terminal]
export TASKQ_AUTH_DSN='postgresql://auth_operator:...@auth-db/app'

taskq auth sync-permissions \
  --queues mail,exports \
  --apply
```

`--queues` is one comma-separated list. Omit `--apply` for a dry-run report;
add `--reconcile` only when the command should reconcile existing rows.
